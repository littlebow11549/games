## 4. 遇到的問題與經驗（Lessons Learned）

1. **部署可見性是最大時間黑洞**。使用者多次「沒看到改變」，根因有三：
   - 瀏覽器**快取** JS/CSS/圖片（最常見）。
   - GitHub Pages build **排隊變慢**（偶爾 5–7 分鐘）。
   - 一次 Pages **deploy 步驟失敗**（build 成功但 deploy 失敗，重跑又卡 queue）——最終以「推新 commit 觸發全新部署」解決。
   - 經驗：每次改完都要**主動輪詢部署狀態＋抓線上內容驗證**，並明確告知使用者「強制重新整理／加版本參數」。

2. **跨 AI 協作的合併策略**。GPT 分支常基於較舊的程式碼，直接 merge 會與最新的 JS/CSS 衝突。採「**只取素材檔、程式自接**」最穩，但每次都要人工挑檔。

3. **殘留 CSS 規則造成隱性 bug**。例如舊 `.mascot canvas{scale(1.62)}` 殘留，使新待機 canvas 被放大 1.62 倍；Hub `.banner{min-height:0}` 精簡模式使橫幅被壓扁切掉 Logo。清理舊規則與量測計算值（computed style）才找得到。

4. **響應式背景圖的安全區**。橫幅在矮視窗被 `cover` 置中裁切會切到重點——需在**美術構圖階段**就預留中央安全帶。

5. **低解析→重做的來回**。先交小圖字藝再要 hero 版，造成二次工。應一開始就要 hero 解析度。

6. **視覺迭代需要即時預覽**。本次大量使用 Playwright 截圖（指定 430×820、deviceScaleFactor 2）即時驗證，是加速關鍵。

## 5. 反覆修正清單（執行中做得不夠好、來回多次的地方）

誠實檢討：以下是使用者需要講好幾次、或我改好幾次才對的地方，以及真正原因。

1. **漂浮寶石（反覆約 4–5 次，最嚴重）**
   - 過程：3.2x「還是太小」→ 5.5x「太大又亂」→ 對稱排列「太工整」→ 散佈景深才定版。
   - 原因：我**每次都過度修正**（太小→太大→太整齊），用「猜一個值→截圖」試，而不是一次給出「大小有層次＋自然散佈」的設計意圖。
   - 下次：對這類主觀視覺，第一次就提供 **2–3 個明顯不同的選項**讓使用者挑，而不是單一值來回逼近。

2. **部署可見性（反覆最多次：沒看到改變 / 還沒看到最新版 / 有上傳正式嗎）**
   - 過程：多次回報「已部署」，但使用者看不到；最後才發現有一次 **Pages deploy 步驟真的失敗了**。
   - 原因：我**太早說「已上線」卻沒先抓線上內容驗證**；把「push 成功」「build 成功」當成「使用者看得到」。失敗那次也拖到使用者再催才查出。
   - 下次：**改完→抓線上實際內容比對→才回報**，一律附「強制重新整理」；偵測到 deploy 失敗立刻自動重觸發，不等使用者催。

3. **待機動畫上線即「巨大蓋住 logo」（使用者截圖才發現）**
   - 原因：舊 `.mascot canvas{scale(1.62)}` 殘留規則沒先清，導致新 canvas 被放大 1.62 倍。我**在截圖驗證時其實已修好，但使用者看到的是部署快取的壞版**，加上我沒先排查殘留 CSS。
   - 下次：換元件時先 grep 清掉所有針對舊元件的規則；上線前以 computed style 量測確認尺寸。

4. **Banner（churn 最大：02→03→填滿→手機 Logo→改回→換最初 banner_01→全部作廢）**
   - 原因：我一直用 **CSS 微調去救構圖問題**，沒有早點判斷「這是構圖/方向問題」並確認使用者到底要哪個方向；最後使用者其實要的是**最一開始那張**。
   - 下次：方向性的東西**先確認方向再動手**；大改前先問「要延續還是回到某個版本」。

5. **字藝先用低解析、再換 hero（二次工）**
   - 原因：先接了小圖單詞字藝，之後才換 1774px hero 版。
   - 下次：標題類字藝一律等/要 hero 解析度，不用低解析暫代。

6. **語音轉文字的模糊指令**
   - 我多為合理推測（多半正確），但有一兩次是猜的。下次對明顯亂碼的關鍵指令，先用一句話覆述確認再動工。

## 6. 下一個遊戲專案的改進建議

### A. 速度提升（開發/部署流程）

1. **資產快取破壞（cache-busting）機制**：runtime 檔名帶內容雜湊或版本（如 `pug_idle_full.ab12.webp`），或建置時統一加 `?v=<hash>`。使用者永遠看到最新，直接消滅「沒看到改變」的來回。
2. **一鍵部署驗證腳本**：封裝「輪詢 Pages run → 抓線上關鍵檔案 → 比對是否為新版」的檢查（本次已手動做過多次），每次 push 後自動跑，部署失敗自動重觸發。
3. **本地預覽工作流從第一天就建**：把 Playwright 截圖 harness（多畫面、多尺寸、console/404 檢查）做成專案內的 `tools/preview.js`，迭代不必等部署。
4. **建置化的素材管線**：一支 `tools/build_assets.py`，由 source 母檔**自動產生 runtime lossy WebP（降尺寸＋壓縮）＋ manifest**，取代逐檔手動壓縮。
5. **美術協作協定**：與美術 AI 約定「**美術分支只動 `assets/`、不碰程式**」，並從 Claude 最新 commit 開分支，讓合併零衝突。
6. **先定規格再開工**：尺寸、透明、命名、安全區、hero 解析度一次講清楚，減少重做。

### B. 設計品質與產量提升

1. **建立設計系統 / 風格 token**：把本作的視覺語言（金色立體字＋深藍描邊＋頂光＋水晶/能量帶、12 色寶石、青光）文件化成 style guide，讓美術能**成批**產出一致素材，而非一張張試。
2. **一次規劃完整素材清單再批量生成**：KV 主視覺、角色各狀態（待機/開心/失落/慶祝 sprite）、整套字藝（標題＋按鈕＋橫幅詞）、UI 九宮格、數字、SFX/BGM、影片——先列全表，讓美術批次交付，避免滴水式來回。
3. **一律交 hero 解析度**（≥1774px / 角色方格 ≥1024px）＋ 透明去背，runtime 再降尺寸；源頭就高品質。
4. **響應式安全區規範**：所有「當背景用」的圖，重點元素落在中央安全帶、邊緣留負空間（橫幅教訓）。
5. **元件化可重用模組**（跨遊戲帶走）：
   - 字藝標題元件（`<img class="title-word">` + 置中 CSS 模式）
   - 漂浮寶石模組（`floatgems.js`，sprite + 景深參數）
   - 待機動畫驅動（`hero-idle.js`，8 格 sprite 通用驅動）
   - 遊戲中心 Hub（多語系、分類、最愛、卡片）
6. **源碼/廢案分離制度**：source 母檔（無損）＋ runtime（lossy）＋ `_archive/`（廢案）三分，從頭維持，避免後期大整理。
